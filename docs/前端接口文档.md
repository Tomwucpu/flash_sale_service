> 文档版本：v1.0  
> 编写日期：2026-04-28  
> 适用范围：`frontend` 目录下当前 Vue 3 + TypeScript 前端实现  
> 当前阶段：仅描述当前代码中已经接入并在页面上实际使用的前端路由、接口调用、鉴权规则与交互约定

## 1. 文档范围

本文档基于以下当前源码整理：

- `frontend/src/api/*.ts`：前端 API 封装
- `frontend/src/router/*.ts`：前端路由与访问控制
- `frontend/src/stores/auth.ts`：登录态持久化
- `frontend/src/views/**/*.vue`：页面级接口调用与交互流程
- `frontend/src/utils/activity-form.ts`、`frontend/src/utils/export-task.ts`、`frontend/src/utils/date.ts`：请求参数组装与轮询/导出辅助逻辑

本文档的重点不是重复后端接口样例，而是说明：

- 前端有哪些页面入口与路由守卫；
- 每个页面会调用哪些后端接口；
- 前端请求头、鉴权、错误处理、轮询与导出采用什么约定；
- 页面真实使用了哪些请求/响应字段。

如需查看后端接口的完整请求/响应示例，请同时参考 `docs/后端接口文档.md`。

## 2. 运行与访问约定

### 2.1 前端访问入口

- 默认开发地址：`http://localhost:5173`
- 默认 API 代理：`frontend/vite.config.ts` 将 `/api` 代理到 `http://localhost:18080`
- 如果需要绕过本地代理，可通过环境变量 `VITE_API_BASE_URL` 覆盖 API 基址

### 2.2 登录态与本地存储

- 登录态存储键：`flash-sale-auth`
- 存储内容：`accessToken` 与当前用户 `user`
- 应用启动时会先从 `localStorage` 恢复登录态
- 当前启动流程**不会自动调用** `GET /api/users/me` 做二次刷新，页面守卫与布局展示主要依赖本地已持久化的用户信息

### 2.3 鉴权与自动跳转

前端路由守卫规则如下：

| 路由类型 | 规则 |
| --- | --- |
| `/public/**` | 公开访问 |
| `/login`、`/register` | 未登录可访问；已登录会自动跳到后台或用户工作台 |
| `/user/**` | 需要登录 |
| `/admin/**` | 需要登录，且角色为 `ADMIN` 或 `PUBLISHER` |

已登录用户访问登录/注册页时：

- `ADMIN` / `PUBLISHER` 会被重定向到 `/admin/activities`
- `USER` 会被重定向到 `/user/orders`

### 2.4 请求头与超时规则

所有通过 `frontend/src/api/http.ts` 发起的请求都有以下约定：

- 自动生成 `X-Request-Id`
- 如果本地存在 `accessToken`，自动带上 `Authorization: Bearer <token>`
- 默认超时时间 `10000ms`

补充说明：

- 后端文档里说明服务端不会自动生成 `X-Request-Id`，但当前前端封装层会在浏览器侧统一补齐
- 秒杀尝试接口 `POST /api/seckill/activities/{activityId}/attempt` 依赖该请求头，当前前端无需页面单独处理

### 2.5 401 处理规则

当接口返回 `401` 时，前端会：

1. 清空本地会话；
2. 删除 `flash-sale-auth`；
3. 如果当前页不是 `/login`，自动跳转到 `/login`。

## 4. API 封装层说明

### 4.1 `authApi`

| 方法 | HTTP | 路径 | 返回数据 | 使用页面 |
| --- | --- | --- | --- | --- |
| `register(payload)` | `POST` | `/api/users/register` | `UserProfile` | `/register` |
| `login(payload)` | `POST` | `/api/users/login` | `LoginResponse` | `/login` |
| `me()` | `GET` | `/api/users/me` | `UserProfile` | 当前仅 `authStore.fetchMe()` 预留，启动流程未自动调用 |
| `getUserById(userId)` | `GET` | `/api/users/{userId}` | `UserProfile` | 当前页面未直接使用 |

页面侧实际行为：

- 注册页会先做前端校验，再调用 `register`
- 登录页通过 `authStore.login()` 间接调用 `login`
- 登录成功后会把 `accessToken` 与 `user` 一起写入本地存储

## 5. 页面级交互流程

### 5.1 登录与注册

#### 注册页 `/register`

前端校验规则：

- 用户名不能为空
- 确认密码不能为空
- 两次输入密码必须一致
- 密码长度必须在 `8-64` 位
- 昵称、手机号为空时会转成 `undefined`

注册成功后：

- 弹出成功提示
- 自动跳转到 `/login`
- 并通过 `query.username` 回填登录页用户名

#### 登录页 `/login`

登录成功后：

- 调用 `authStore.setSession()` 写入本地会话
- 如果 URL 上带有安全的 `redirect` 参数，则优先跳转该地址
- 否则：
  - `ADMIN` / `PUBLISHER` 跳到 `/admin/activities`
  - `USER` 跳到 `/user/orders`

### 5.2 公开活动详情与秒杀链路

页面：`/public/activities/:id`

首次进入页面时：

1. 加载活动详情 `GET /api/public/activities/{id}`
2. 如果已登录，继续查询：
   - 当前活动秒杀结果 `GET /api/seckill/results/{id}`
   - 当前用户在该活动下的订单列表 `GET /api/orders/activities/{id}`

点击“立即抢购”时：

1. 前端先检查：
   - 是否已登录；
   - 活动是否 `PUBLISHED`；
   - 活动阶段是否 `ONGOING`；
2. 然后调用 `POST /api/seckill/activities/{id}/attempt`
3. 如果返回业务码 `SECKILL_PROCESSING`：
   - 提示请求已受理；
   - 立即刷新一次秒杀结果；
   - 如果状态为 `PROCESSING` 或 `PENDING_PAYMENT`，启动轮询

轮询规则：

- 轮询间隔：`2500ms`
- 继续轮询的状态：`PROCESSING`、`PENDING_PAYMENT`
- 页面卸载或用户退出登录时会停止轮询

支付活动的模拟支付流程：

1. 当秒杀结果状态为 `PENDING_PAYMENT` 且存在 `orderNo` 时，显示支付面板
2. 点击“创建模拟支付单”：
   - 调用 `POST /api/payments/orders/{orderNo}`
3. 点击“提交模拟支付回调”：
   - 调用 `POST /api/payments/callback`
   - 请求体为 `orderNo + transactionNo`
4. 回调成功后：
   - 重新查询秒杀结果；
   - 如果仍需等待，继续轮询；
   - 否则静默刷新当前活动订单列表

### 5.3 用户订单页

页面：`/user/orders`

核心行为：

- 进入页面后调用 `GET /api/orders`
- 提供“刷新”按钮重新加载
- 根据响应字段展示：
  - 订单号
  - 活动 ID
  - 订单状态
  - 支付状态
  - 发码状态
  - 兑换码
  - 异常原因
  - 更新时间

### 5.4 后台活动管理页

页面：`/admin/activities`

核心行为：

- 进入页面后调用 `GET /api/activities`
- 支持从列表直接触发：
  - 立即发布
  - 提前发布
  - 下线
  - 删除
- 成功后统一重新加载活动列表

按钮显隐逻辑：

- 仅 `publishStatus === UNPUBLISHED` 时显示发布按钮
- 仅可编辑活动时显示编辑按钮
- `publishStatus !== OFFLINE` 时显示下线按钮
- 删除按钮始终展示，但只有 `UNPUBLISHED` / `OFFLINE` 可点击

### 5.5 活动新建与编辑页

页面：`/admin/activities/create`、`/admin/activities/:id/edit`

请求行为：

- 新建页直接提交 `POST /api/activities`
- 编辑页先加载 `GET /api/activities/{id}`，再提交 `PUT /api/activities/{id}`

前端请求体组装规则：

- 日期字段统一格式化为 `YYYY-MM-DD HH:mm:ss`
- `needPayment = false` 时，强制把 `priceAmount` 置为 `0`
- `purchaseLimitType = SINGLE` 时，强制把 `purchaseLimitCount` 置为 `1`
- `publishMode = IMMEDIATE` 时，不提交 `publishTime`
- `publishMode = SCHEDULED` 且缺少 `publishTime` 时，前端直接报错，不发请求

### 5.6 活动详情与兑换码导入

页面：`/admin/activities/:id`

核心行为：

- 进入页面后先加载 `GET /api/activities/{id}`
- 如果活动采用第三方兑换码：
  - 自动加载导入批次列表 `GET /api/activities/{id}/codes/import-batches`
  - 支持上传 `csv/xlsx`
  - 支持查看单个批次详情 `GET /api/activities/{id}/codes/import-batches/{batchNo}`

导码页面规则：

- 仅 `publishStatus === UNPUBLISHED` 时允许执行导入
- 导入成功后会刷新批次列表
- 最近一次导入结果会直接在页面上展示成功/失败统计与失败行

### 5.7 发布方订单页与兑换码导出

页面：`/admin/activities/:id/orders`

进入页面时会并行请求：

- `GET /api/activities/{id}`
- `GET /api/orders/admin/activities/{id}`

导出流程：

1. 点击“导出已售兑换码”
2. 调用 `POST /api/exports/tasks`
3. 如果任务未立即成功，则每 `1000ms` 轮询一次 `GET /api/exports/tasks/{taskId}`
4. 最多轮询 `30` 次
5. 成功后从 `fileUrl` 中提取文件名，再调用 `GET /api/exports/files/{fileName}` 下载二进制内容
6. 通过浏览器 `Blob + a.download` 触发保存

失败条件：

- 任务状态为 `FAILED`
- 轮询超时
- 任务完成但未返回 `fileUrl`

## 7. 联调注意事项

- 页面如果直接使用浏览器访问后端接口，建议统一走 Gateway：`http://localhost:18080`
- 本地前端联调默认依赖 Vite 代理；若代理关闭，需要自行提供 `VITE_API_BASE_URL`
- 当前前端大量依赖后端返回的状态枚举文本：
  - 活动状态：`UNPUBLISHED`、`PUBLISHED`、`OFFLINE`
  - 活动阶段：`PREVIEW`、`ONGOING`、`ENDED`
  - 秒杀结果：`INIT`、`PROCESSING`、`PENDING_PAYMENT`、`SUCCESS`、`FAIL`
  - 订单状态：`INIT`、`CONFIRMED`、`CLOSED`、`FAILED`
  - 支付状态：`NO_NEED`、`WAIT_PAY`、`PAID`、`CLOSED`
  - 发码状态：`PENDING`、`ISSUED`、`FAILED`
- 若后端调整了这些枚举值，前端展示文案、状态色与轮询判定都需要同步修改
- 当前前端没有独立的全局刷新 `/api/users/me` 机制；如果后端 JWT 仍有效但本地 `user` 数据缺失或过旧，页面展示会优先受本地缓存影响
